# context-align — 提问对齐（方向与关键决策）

目标：用「有根据的、判别性的提问」代替猜测——每个问题必须通过实质闸门（答案不同 → 行动不同）、必须带知识库证据或声明为空白；每轮收敛一个决策点；最终产出：明确的方向 + 决策清单 + 假设台账，并沉淀回知识库（否则下次会话丢失）。

## 步骤

1. **环境自检**：同 context-build（`.venv/Scripts/python index.py ...`）。

2. **装载相关上下文**：`match "用户的话"` → `node show` 建议先读的节点 → `rels` 扩展 → `tut list` 查相关教程。产出一对清单：**已确证**（库里明确支持的事实/约定，引用节点编址）与**悬而未决**（每条标注类型，见步骤 3）。

3. **分类盘点**（先消解话术歧义，再盘库缺口——顺序不能反，意图不清时无法映射到节点）：

   **A. 用户话术歧义**（三种，问法各不同）：
   - **多解歧义**：同一句话有多种合理解读 → 用**选项题**让用户选解读；
   - **欠指定**：缺关键信息（平台？受众？规模？约束？）→ 用**补充题**请用户给出；
   - **指代不明**：「它」「那个方案」指代不清 → 先用节点编址确认指代对象，再继续。

   **B. 库缺口**（上下文装载后对照发现）：
   - **空白**：库里没有相关 tag/project——新方向，还是既有方向的分支？
   - **断裂**：相关节点存在但没互挂（refs/tags 缺失）——关系该不该建立？
   - **规范缺口**：反复出现的决策但无 spec 覆盖——要不要立规？
   - **冲突**：节点之间、或节点与当前诉求矛盾——以哪个为准，还是修订规范？

4. **逐轮提问对齐**（核心循环，每轮收敛一个决策点）：

   - **实质性闸门（每个问题先过闸）**：问自己「**不同答案会让我做不同的事吗？**」
     - 会 → 提问；
     - 不会 → **不问**，记入假设台账（假设 + 依据 + 何时需回头确认），继续下一个点。这条闸门优先于任何提问冲动。
   - **判别性要求**：问题的每个选项必须映射到**不同的后续动作**；若所有选项殊途同归，这个问题不值得问——直接采用推荐项并向用户声明。
   - 一次只问一个问题（最多两个紧密相关的小问题），先问影响最大的；
   - 每个问题**必须带证据**：引用节点编址与内容（如「`project:x` 的范围是 A，不含 B」）；库里没有的，明确声明「库里空白，这是新决策」；
   - 给默认建议：基于库内证据给推荐项与理由，用户可一句话确认；
   - 答案落定即记入「决策清单」，并顺势问一句是否沉淀；
   - 停止条件：方向与关键决策均有结论，且闸门后无剩余问题。单次会话一般 ≤5-7 问；被闸门拦下的小决策进入假设台账。

5. **沉淀结论**（按结论类型走对应流程）：
   - 新主题 → `node add tag`；新方向/项目 → `node add project` + 挂 tag；
   - 可复用的关键决策 → `spec add` 立规（转 spec-manage），相关节点 `--add-ref` 挂接；
   - **非规范级的关键决策** → 写入相关 project/tag 节点正文 `## 决策记录`，格式采用 MADR-lite：**背景 / 决策驱动 / 选项（含被否选项与否决原因）/ 结论 / 后果**——被否选项必须记录，否则半年后不知道为什么没走另一条路；
   - 外部依据 → `ref add`（转 reference-add）；
   - 范围/边界变化 → 编辑节点正文（## 范围）或 `node set` 改元数据；**手改后 rebuild**；
   - 填完内容必须清除模板占位（check 会检测）。

6. **收尾**：`check` 自检 → 向用户复述四件套：**方向结论 + 决策清单 + 假设台账**（假设/依据/回头确认时机）+ 本次沉淀的节点与遗留开放问题。建议 git commit（不确定时先问）。

## 提问模板（按类型区分问法）

- **多解歧义 → 选项题**：「这句话有两种理解：① …（走动作 A，比如建 `tag:a`）；② …（走动作 B，比如扩展 `project:x`）。哪种符合你的意思？」
- **欠指定 → 补充题**：「要落库还缺关键信息：目标平台/受众/规模是什么？」
- **指代不明 → 消解题**：「你说的『那个方案』是指 `tag:a` 里的做法，还是 `reference:b` 提到的做法？」
- **方向类（库空白）**：「库里没有这个主题的节点。它是新方向（我建 tag + project），还是某个既有方向的子问题（挂到 `tag:x` 下）？」
- **规范类（冲突）**：「这个做法与 `SPEC-001` 第 3 条冲突：按规范调整（推荐），还是这是例外需要修订规范？」
- **取舍类（判别示例）**：「两个方案：`tag:a` 的资料支持方案一，`reference:b` 支持方案二；按 `project:y` 的目标看方案一更近。默认选方案一，除非你有其它约束？」

## 规则

- **实质闸门**：答案不会改变后续行动的问题一律不问，降级为假设台账；
- **判别性**：选项必须对应不同后续动作，殊途同归不问，直接声明推荐项；
- **每个问题必须带依据或声明为空白**——禁止无根据的泛泛提问；
- 禁止一次抛一堆问题；能用合理默认的小决策不问，问题宁少勿多；
- 引用节点一律用编址（`tag:x` / `SPEC-001` / `reference:y`），方便用户回查；
- 对齐结论必须落盘（frontmatter / 正文 / 新节点 / 决策记录），未落盘等于没对齐；
- 收尾主动询问是否 commit。

## 禁止

- 不看库就问「你想怎么做」——先 match 装载上下文再问；
- 把用户答案只留在对话里不沉淀；
- **问卷式连环提问**——被实质闸门拦下的问题，哪怕凑不满一轮也一个都不问；
- 超 ~7 个问题仍在原地打转——说明缺口太大，先建议建节点补库，再继续对齐；
- 替用户拍板方向性决策（默认项可以建议，但方向与关键决策必须用户确认）。
